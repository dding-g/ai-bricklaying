[한국어](README.ko.md)

`ai-bricklaying` turns today's AI coding history into an interview-confirmed worklog. It installs a reusable skill so you can say “write today's worklog” in your AI conversation, verify the proposed task titles, add how the work felt, and resume later on the same local date if you stop midway.

## What It Does

- Installs an AI-activity-informed daily worklog skill, with a user-recall fallback, into one or more AI agent skill directories. New installs default to Claude Code.
- The generated daily skill sends all five catalog keys—OpenCode, Claude Code, Codex, Cursor, and GitHub Copilot—and reports per-source coverage. Adapter support differs by source and schema; this is not a claim that every history format is readable. The legacy summary still uses one `--sources` value.
- Before consent, the generated skill shows only provider/source names, status, and record counts from the evidence-withheld `prepare` response. It asks for an explicit yes/no decision before any excerpt is disclosed.
- Proposes up to six work titles with stable numbers, a one-line basis, and uncertainty; supports accept, rename, merge, split, exclude, missing-work additions, or an explicit “no work to record” decision.
- Conducts a one-question-at-a-time, 3-5 minute reflection and saves progress after every answer.
- Uses deterministic Korean or English interview and worklog templates. A different legacy summary language is normalized to English for the daily flow.
- Saves confirmed worklogs locally as private Markdown and structured JSON; the CLI remains the sole state writer.
- Keeps the existing single-source lightweight summary command for compatibility.
- Saves a lightweight Markdown summary using `YYYY-MM-DD-ai-bricklaying-daily-summary.md`.
- Writes metadata to `ai-bricklaying-summary-skill.json`.
- Optionally prepares Gmail MCP delivery details for the legacy lightweight summary.
- Optionally creates a Slack-ready payload from the legacy lightweight summary.
- Stores setup defaults in `~/.config/ai-bricklaying/config.json` so the next run can reuse them.

## Requirements

- npm or npx
- Node.js 18 or newer when you run the npm or npx launcher
- A first-release supported platform: `darwin-arm64`, `darwin-amd64`, `linux-amd64`, or `linux-arm64`
- A host that can run the local `ai-bricklaying` command and read the catalog adapter inputs you intend to use

The CLI behavior is implemented by a bundled Go binary. The npm package keeps `bin/ai-bricklaying.js` as a small launcher that selects the matching binary and forwards your command.

## Install

```bash
npm install -g ai-bricklaying
ai-bricklaying --help
```

Or run without installing:

```bash
npx ai-bricklaying --help
```

`npx` is useful for previewing or running setup once. The reusable skill later invokes `ai-bricklaying` from the host's local shell, so install it globally (or otherwise put it on `PATH`) and allow Claude access to the local command and source files.

Check your installed version:

```bash
ai-bricklaying --version
```

If your platform is not one of the bundled first-release targets, the launcher exits with an unsupported platform message instead of falling back to a different implementation.

Generated skills use target-specific defaults: `~/.claude/skills` for Claude Code, `~/.codex/skills` for Codex, `~/.cursor/skills` for Cursor, and `~/.config/opencode/skills` for OpenCode. GitHub Copilot uses `$COPILOT_HOME/skills` when `COPILOT_HOME` is set, otherwise `~/.copilot/skills`. Without an explicit `--skill-dir`, a saved default from an older release is migrated for a single Copilot target; custom paths and shared multi-target paths are preserved.

If a user-authored skill with the same name already exists at a destination, setup stops instead of overwriting it. Only a skill generated by `ai-bricklaying` for the same config and name, or an exactly recognized generated skill from an earlier release, can be updated in place.

## Quick Start

Install the Claude Code skill.

```bash
npm install -g ai-bricklaying
ai-bricklaying \
  --non-interactive \
  --target-agent claude-code \
  --sources claude-code \
  --language Korean \
  --output-modes file
```

Start the worklog in Claude Code.

```text
Write today's worklog.
```

You can also invoke the skill directly.

```text
/ai-bricklaying-worklog
```

| Goal | Action |
|---|---|
| Start today's worklog | Say `Write today's worklog` |
| Resume an interview | Ask again on the same local date |
| Change setup or refresh the skill | Run `ai-bricklaying` |
| Check the installed version | Run `ai-bricklaying --version` |
| Show every option | Run `ai-bricklaying --help` |

## Interactive Setup

Run:

```bash
ai-bricklaying
```

The wizard asks for:

1. Target AI agents where the generated skill should be installed. You can select multiple targets; Claude Code is the first-run default.
2. One source for the legacy lightweight summary. This choice does not limit the daily worklog profile, which sends all five catalog keys and reports each adapter's actual coverage.
3. Summary language. The legacy lightweight summary keeps this value; the daily interview/worklog supports Korean and English and falls back to English for any other value.
4. File save directory. The default is `~/ai-bricklaying`.
5. Legacy-summary output modes. File save is always enabled; Gmail MCP and Slack webhook are optional. Confirmed worklogs remain local-only.

When generation completes, the CLI prints the generated skill command in bold:

```text
Use the generated skill: /ai-bricklaying-worklog
```

If the target is OpenCode and the skill does not appear immediately, restart OpenCode or open a new session. OpenCode loads skills at session startup.

## Daily Worklog Interview

After setup, start in Claude with a natural-language request such as:

```text
Write today's worklog.
```

The current shipped adapter is the Claude/Claude Code generated skill. Other target directories remain available for compatibility, but this phase validates the end-to-end interview adapter on Claude/Claude Code first. It follows this flow:

1. Check that `ai-bricklaying` is available locally, then call `status`. Resume an unfinished flow for the same local date, or call `prepare` with the explicit list of all five catalog source keys when no flow exists.
2. Show only source, status, and count. Explain that the host may process disclosed data remotely and ask for an explicit yes/no decision.
3. Call `disclose` with explicit `consent`. `true` returns bounded excerpts after best-effort common-credential redaction; `false` persists denial and returns no evidence. Omitting consent is an error and does not advance the flow.
4. Show candidate work titles and let you approve or edit them in plain language, saving each accepted snapshot with `checkpoint`.
5. Ask at most three compact reflection questions, one at a time, and save each answer with `checkpoint`.
6. Show the final preview and call `finalize` only after explicit confirmation.

If you stop, ask for the worklog again later on the same date; the skill resumes from the saved progress. It does not route an older date into today's interview. Every session-derived excerpt remains untrusted data: common credentials are redacted on a best-effort basis, and instructions, URLs, and paths inside an excerpt are never executed.

Strict daily coverage is intentionally schema-specific:

| Catalog key | Shipped strict daily coverage |
|---|---|
| Claude Code | Main-project JSONL under `~/.claude/projects`; `CLAUDE_CONFIG_DIR` replaces that root. Visible user/assistant text is selected by event time. System, tool, metadata, sidechain, memory, and subagent content is excluded. |
| Codex | `sessions` and `archived_sessions` below `CODEX_HOME` (default `~/.codex`); a configured `CODEX_HOME` replaces the default root. For the relevant local day, lifecycle evidence prefers `item_completed`, then direct messages, then response fallback. Context, tool, and reasoning content is excluded; event time is used. |
| Cursor | Privacy-conservative experimental adapter for well-formed JSONL under `~/.cursor/projects/**/agent-transcripts`. It accepts only `role=user` `<user_query>` content and excludes assistant, reasoning, and skill content. File mtime is used only when an event timestamp is absent, and that fallback is labeled in `timestamp_basis`. |
| GitHub Copilot | Experimental VS Code adapter that replays schema-v3 mutations from `workspaceStorage/*/chatSessions` and requires the `GitHub.copilot-chat` extension ID. Hidden, system, tool, thinking, and other-agent content is excluded; unknown or oversized dependent state fails closed instead of being guessed. |
| OpenCode | The current `opencode.db` storage is detected as `unsupported_storage`. `XDG_DATA_HOME` replaces the default `~/.local/share` data root. Only recognized legacy JSON text parts are eligible; logs and auth files are never strict-scanned. |

Coverage status is one of `complete`, `no_activity`, `not_found`, `unreadable`, `parse_error`, `truncated`, `unsupported_schema`, or `unsupported_storage`. The skill shows that status and count before asking for disclosure consent, so unsupported storage or schema is not presented as “no work.”

Strict daily discovery retains at most the newest 5,000 adapter-matched candidates per source with bounded candidate-selection memory. That number is still not a directory-entry, wall-clock, traversal, or total-resource bound.

The Phase 1A daily flow has deterministic Korean and English question/artifact templates. Exact `ko`, BCP-47-style `ko-*`, or a value containing `Korean` or `한국` selects Korean. Every other saved legacy summary language or machine `prepare.language` value selects English for the daily flow.

The skill does not schedule itself. A compatible host scheduler may invoke it at a chosen time only when that host can run the local CLI and access the source files. A scheduled invocation is only a wake-up: it must not infer evidence consent, call `disclose`, finalize a worklog, or deliver anything without the same explicit user decisions as an interactive run. ChatGPT does not consume `SKILL.md` directly; a ChatGPT MCP adapter that reuses the same machine contract is planned, not shipped. Monday-Sunday weekly review is also planned after the daily flow passes dogfood gates; no weekly command or artifact ships in this phase.

## Outputs

Legacy summary artifacts and confirmed worklogs use `--output-dir`, which defaults to `~/ai-bricklaying`. Resumable state uses `--config-dir`, and generated skills use their target skill directories.

- `YYYY-MM-DD-ai-bricklaying-daily-summary.md`: lightweight summary focused on takeaways, improvements, and better AI usage.
- `ai-bricklaying-summary-skill.json`: metadata, selected targets, delivery modes, summary path, and generated skill directories.
- `ai-bricklaying-slack-payload.json`: Slack payload for the legacy lightweight summary when `slack-webhook` is selected.
- `worklogs/daily/YYYY-MM-DD-ai-bricklaying-worklog.md`: local-only user-confirmed worklog, mode `0600` on POSIX.
- `worklogs/daily/YYYY-MM-DD-ai-bricklaying-worklog.json`: confirmed structured sidecar, mode `0600` on POSIX.
- `<config-dir>/state/v1/daily/YYYY-MM-DD.json`: resumable private interview state. It may contain bounded, best-effort-redacted evidence and is not a sharing artifact.
- `<config-dir>/state/v1/daily/YYYY-MM-DD.json.lock` and `<output-dir>/.ai-bricklaying/locks/v1/daily/YYYY-MM-DD.lock`: empty private coordination files that may remain after a run; they are not worklog artifacts.
- `<skill-dir>/<skill-name>/SKILL.md`: generated reusable interviewer skill. It calls the versioned machine protocol and never edits state or worklogs directly.

On POSIX, the private state/worklog/lock directories use mode `0700` and their files use `0600`.

Confirmed JSON and Markdown are published with create-if-absent semantics, so a foreign or mismatched artifact is not replaced. If the process stops after publishing only part of a finalize operation, a retry for the same flow and expected content completes the missing artifact/state and preserves the original confirmation time.

For Agent Skills compatibility, `--skill-name` must be 1-64 characters using lowercase `a-z`, digits, and single hyphens only, with no leading, trailing, or consecutive hyphen. The skill directory and frontmatter name use this exact value; for example, `ai-bricklaying-worklog`.

## Slack Delivery

Select `slack-webhook` to create a Slack-ready payload for the legacy lightweight summary. The CLI prepares local files only; it does not call the webhook for you. Phase 1A confirmed worklogs are local-only, and this payload must not be treated as worklog delivery.

On a Unix TTY, interactive webhook entry disables terminal echo and renders only `[hidden]`; if hidden input cannot be established, the CLI fails closed instead of falling back to echoed input.

Any later webhook call is a separate legacy-summary delivery action and should reconfirm the destination and payload content first.

```bash
ai-bricklaying \
  --non-interactive \
  --target-agent opencode \
  --sources opencode \
  --output-modes slack-webhook \
  --slack-webhook-url "https://hooks.slack.com/services/..."
```

The CLI does not print the webhook secret after it is saved. Existing webhook config is shown as `[configured]` in prompts.

Slack payload behavior:

- The saved Markdown summary is the source of truth for Slack delivery.
- The Slack payload is generated from the finalized Markdown; it is not shortened or rewritten unless you explicitly ask for a Slack-specific summary.
- Markdown sections and bullets stay in order. Large summaries are split into a `messages` array only to satisfy Slack block length limits.
- The first batch is also exposed as top-level `text` and `blocks` for simple webhook usage. Send `blocks` to render headings and lists properly.
- The payload includes verification metadata showing whether every top-level Markdown section is covered.

## Gmail MCP Delivery

Select `gmail-mcp` when you want the legacy lightweight summary instructions and metadata to include Gmail MCP delivery details. The CLI prepares handoff details only; it does not send email. This mode does not deliver a confirmed worklog.

```bash
ai-bricklaying \
  --non-interactive \
  --target-agent opencode \
  --sources opencode \
  --output-modes gmail-mcp \
  --gmail-recipient team@example.com \
  --gmail-subject "AI session summary"
```

The generated skill marks this as a legacy-summary handoff and tells the agent to use Gmail MCP only when this mode was selected. Any actual handoff is a separate legacy-summary delivery request and must reconfirm the destination and content; it is never a confirmed-worklog send.

## Config Defaults

The CLI stores local configuration at:

```text
~/.config/ai-bricklaying/config.json
```

Saved config includes delivery settings and defaults such as target agents, source, language, output modes, skill name, skill directory, and output directory. On the next run, the CLI reads this file and uses those values as defaults.

For compatibility, a saved lowercase legacy skill name that uses only letters, digits, dots, underscores, and hyphens is migrated to the strict single-hyphen slug form on the next successful run (for example, `legacy_summary` becomes `legacy-summary`). Explicit `--skill-name` values remain strict, and unsafe saved values are rejected rather than rewritten. A legacy invocation that explicitly supplies one known `--sources` value without `--target-agent` uses that source as its sole target; an explicit target/source mismatch still fails.

The saved `language` remains the legacy lightweight-summary setting. When it is reused by the daily machine flow, only Korean and English are supported; other values fall back to English.

Command-line flags always override saved config. Use `--config-dir` to use a different config location for tests or automation.

## Keeping It Updated

Update the npm package, including its bundled Go binary, then run the CLI again to refresh the generated skill:

```bash
npm install -g ai-bricklaying@latest
ai-bricklaying
```

The CLI reuses your saved config as defaults, so refreshing usually means accepting the existing prompts and regenerating `SKILL.md`. If you installed the skill into OpenCode, restart OpenCode or open a new session after regenerating it.

## Non-Interactive Example

```bash
ai-bricklaying \
  --non-interactive \
  --target-agent claude-code \
  --sources claude-code \
  --language Korean \
  --output-modes gmail-mcp,slack-webhook \
  --gmail-recipient team@example.com \
  --gmail-subject "AI session summary" \
  --slack-webhook-url "https://hooks.slack.com/services/..." \
  --output-dir ~/ai-bricklaying \
  --skill-name ai-bricklaying-worklog
```

Rules for non-interactive runs:

- `--target-agent` accepts a comma-separated list.
- `--sources` accepts exactly one source.
- `--sources` must be one of the selected target agents.
- `--output-modes` accepts `file`, `gmail-mcp`, and `slack-webhook`; `file` is always enabled.

## CLI Options

```text
--non-interactive                 Use defaults and flags without prompting
--target-agent <agents>           Skill targets: opencode,claude-code,codex,cursor,github-copilot
--target-model <label>            Model label recorded in generated artifacts
--sources, --sessions <source>    Single session source to summarize
--language <language>             Language for the generated summary [English]
--output-modes, --delivery <list> file, gmail-mcp, slack-webhook; file is always enabled
--skill-name <slug>               Generated skill directory name
--skill-dir <dir>                 Directory where the skill folder is written
--output-dir <dir>                Root directory for legacy summaries and confirmed worklogs [~/ai-bricklaying]
--gmail-recipient, --gmail-to     Gmail MCP recipient
--gmail-subject <subject>         Gmail MCP subject
--slack-webhook-url <url>         Slack incoming webhook URL
--config-dir <dir>                ai-bricklaying config directory
-v, --version                     Show CLI version
-h, --help                        Show help

Machine protocol (JSON stdin/stdout):
ai-bricklaying machine daily <prepare|status|disclose|checkpoint|finalize>
protocol_version: 1.0 (required in every request and returned in every envelope)
```

Each machine command accepts exactly one stdin JSON object and returns exactly one stdout JSON envelope. `prepare` and `status` return evidence-withheld public flow control metadata plus source coverage; the skill shows only provider/source/status/count before consent. If `prepare.sources` is omitted, the service falls back to the saved configured summary source or `claude-code`; the generated worklog skill does not omit it and explicitly sends all five catalog keys. Mutations require `flow_id`, `date`, `expected_revision`, and `idempotency_key`. Only `disclose` with `consent: true` returns evidence; `consent: false` persists denial, while omitted consent is an error.

For daily machine requests, `language` resolves to the deterministic Korean or English worklog locale. Unsupported or unrecognized values fall back to English; they do not request arbitrary-language question generation.

## Project Guide

### How It Works

1. The npm launcher runs the bundled Go binary.
2. Setup saves config and target-specific generated skills.
3. The generated skill calls the daily machine protocol.
4. Source adapters collect daily records and coverage states.
5. Only user-confirmed results become private worklogs.

### Main Directories

| Path | Responsibility |
|---|---|
| `bin/ai-bricklaying.js` | Public npm CLI launcher |
| `cmd/ai-bricklaying` | Go CLI entrypoint |
| `internal/cli` | Setup, legacy summary, and CLI contracts |
| `internal/worklog` | Daily protocol, state, and confirmed artifacts |
| `internal/sources` | AI history source adapters |
| `internal/safeio` | Redaction, private writes, and no-clobber publishing |
| `internal/skill` | Generated `SKILL.md` renderer and installer |
| `ssot` | Product and external interface source of truth |
| `tests` | npm launcher and CLI acceptance tests |

### Source of Truth and Outputs

- Update `ssot` contracts before changing user behavior.
- Keep `README.md` and `README.ko.md` synchronized.
- Generated summaries, state, and worklogs are not product sources.
- Confirmed worklogs currently remain local-only.
- Read the [release notes](RELEASE-NOTES-ai-bricklaying-worklog.md) for full context.
